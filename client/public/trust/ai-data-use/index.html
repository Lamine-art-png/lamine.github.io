AI & model data use

Inference is not permission for unlimited reuse.

AGRO-AI separates model inference, customer-specific retrieval, evaluation and model training. Using intelligence features should not silently convert a customer's operational records into training data for unrelated customers.

1. “AI use” is not one thing

Inference

Sending authorized context to a model to answer a request, analyze evidence or perform an approved workflow.

Customer-specific retrieval

Using one customer's authorized records, indexes or configuration to improve responses only within that customer's scope.

Evaluation & safety

Controlled testing for quality, reliability, abuse, debugging or security using authorized, synthetic or appropriately protected data.

Training / fine-tuning

Changing shared model parameters or learned behavior using a dataset. This is governed separately from ordinary inference.

2. Shared-model training boundary

AGRO-AI policy: Customer Data is not used to train shared AGRO-AI models or third-party foundation models for the benefit of unrelated customers unless the customer has expressly authorized that use through an appropriate agreement or control.

Any future program that uses identifiable or customer-linked operational data for shared training requires a documented purpose, data-governance review, contractual authority, appropriate customer notice/choice and the safeguards required by applicable law and agreement.

This rule does not prevent authorized inference, retrieval, security, support, debugging or service evaluation; those activities are separately governed and should use only the data reasonably necessary for the approved purpose.

3. Inference does not create blanket reuse rights

When a user asks AGRO-AI to analyze a field record, report, controller event, photo, transcript or connected dataset, the system may process the necessary customer-authorized context to provide that feature. That authorization does not, by itself, authorize sale, advertising use, unrestricted secondary use or shared-model training.

4. External model-provider controls

A third-party model provider may process data only for reviewed product purposes. Before a material provider or endpoint is used with Customer Data, AGRO-AI's governance standard requires review of:

  • the exact provider, product and API endpoint;
  • the categories of data that may be sent;
  • provider retention behavior and configurable retention settings;
  • whether submitted data may be used for provider training or product improvement;
  • security and confidentiality terms;
  • processing locations and transfer implications where relevant;
  • downstream subprocessors where relevant;
  • deletion/export implications;
  • the approved use cases, risk tier, owner and review date.

AGRO-AI will not describe a provider path as “zero retention” unless the exact account, endpoint and configuration support that statement.

5. Tenant isolation happens before retrieval

Authorization, organization scope and workspace/tenant filtering are applied before data is retrieved and assembled for a model. Cross-customer data should never be fetched first and left for a prompt to separate later.

This is a core architecture rule because model behavior is not an authorization system.

6. Secrets do not belong in model context

Passwords, private keys, API keys, OAuth refresh tokens, connector secrets and equivalent credentials must not be placed in ordinary model prompts or retrieval context. Integration secrets are handled through dedicated credential/storage boundaries rather than treated like normal customer content.

7. Minimize model context

Model context should contain only what is reasonably necessary for the authorized task. AGRO-AI prefers scoped retrieval, structured records and bounded evidence over transmitting an entire customer account, drive, connector or historical dataset “just in case.”

Context minimization reduces security exposure, cross-purpose reuse and irrelevant model behavior at the same time.

8. Provenance and derived intelligence

Where decision quality or auditability matters, AGRO-AI designs workflows to preserve meaningful links between source evidence and generated outputs. Systems should distinguish source records, normalized records, derived features, model-generated conclusions, human edits and final approved actions.

A derived recommendation does not erase the governance obligations attached to the source data. Rights in Customer Data, service telemetry, de-identified/aggregated data, feedback and model outputs are defined by the applicable agreement rather than assumed from the fact that software computed something.

9. De-identification is not just removing a name

Farm data can remain identifying at the operation level even after a company or person name is removed. Field geometry, precise location, rare crop combinations, equipment identifiers, imagery and production patterns can reveal an operation.

Information described as de-identified or aggregated should use an approved method appropriate to the risk and purpose, including review of reasonable re-identification risk.

10. Human control for consequential workflows

For workflows capable of materially affecting crop treatment, irrigation/water application, compliance submissions, financial decisions, equipment operation or comparable consequential activity, AGRO-AI uses risk-appropriate approval, authorization, confidence/uncertainty handling and evidence visibility.

No model receives physical actuation authority merely because it can generate a recommendation. Product capability and authorization must explicitly permit the action.

11. Evaluation, debugging and red-teaming

Customer-linked information used for evaluation, debugging, red-teaming or quality analysis requires documented authority, access restrictions, purpose and retention. Synthetic or appropriately de-identified test data should be preferred for repeatable evaluation when it can provide the needed signal.

Evaluation datasets are not exempt from data governance simply because their purpose is “improving AI.”

12. Customer-specific memory and learning

If AGRO-AI creates customer-specific retrieval indexes, memory, fine-tunes, adapters or other persistent learning artifacts, the product and applicable agreement should make clear:

  • whether the artifact is isolated to that customer;
  • which source data created it;
  • who can access it;
  • how long it persists;
  • whether it can be exported or deleted; and
  • what happens when the customer terminates the service.

13. Voice, transcription, images and other multimodal inputs

Voice recordings, live transcripts, images, video and geolocation-linked evidence can carry additional sensitivity. AGRO-AI treats these inputs as customer content and applies the same authorization, tenant, model-provider and retention governance rules. A user should not assume that changing the input format from text to voice changes the underlying data rights.

Where a voice or transcription provider is used, it is subject to third-party review appropriate to the data handled and the product configuration.

14. Launch gate for new models and providers

No material model-provider, training workflow, cross-customer dataset or AI data-use change should move into production until the data categories and purpose are registered; privacy/security/vendor review is complete; provider terms are reviewed; retention/training settings are verified; authorization and tenant boundaries are tested; and public/customer disclosures are updated where required.

Transparency rule: AGRO-AI will not use a generic “we use AI” disclosure to hide materially different data uses. Inference, customer-specific retrieval, evaluation and training are separate governance decisions.
