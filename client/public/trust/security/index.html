Security

Security is a system of controls, not a badge.

AGRO-AI's security program is designed around enterprise agricultural data, organization boundaries, connected systems, scoped credentials, auditability and controlled change. We publish what we can support and avoid certification claims we have not earned.

1. Security principles

Least privilege

Users, service accounts, connectors and internal access should receive only the permissions needed for the approved purpose.

Tenant boundaries

Organization scope is enforced before protected data retrieval rather than left to downstream application or model behavior.

Server authority

Protected access, entitlements and consequential permissions are enforced by server-side controls.

Evidence-backed claims

Security language should map to actual architecture, configuration, testing, contracts or operating evidence.

2. Architecture boundaries

AGRO-AI separates public marketing surfaces, authenticated product surfaces, API edges, backend services, connector processing and customer-scoped data paths. Public browser clients are not intended to receive permanent server secrets or private upstream credentials.

Where AGRO-AI uses Cloudflare edge controls and authenticated product routing, the public edge is treated as a security boundary for request handling, origin policy, security headers and exposure of private upstream services.

Design rule: a user interface is not an authorization layer. Protected access decisions must remain enforceable even if a client is modified or bypassed.

3. Identity, authentication and authorization

  • Organization and workspace permissions are scoped to the authenticated account and authorized role.
  • Privileged actions should require server-side authorization and appropriate role/entitlement checks.
  • Service accounts and API credentials should be scoped, revocable and attributable.
  • Human administrative access should be limited to legitimate need and reviewable.
  • Access should be removed when a user, integration or service no longer requires it.

4. Credentials and secrets

Permanent secrets belong in server-side secret-management boundaries, not frontend bundles, ordinary logs, analytics events or model prompts. Connector tokens, API keys, private keys and equivalent credentials are handled separately from customer content.

AGRO-AI's AI architecture specifically prohibits placing connector credentials or secrets in ordinary model context. Secrets and credentials should be rotatable or revocable where the underlying provider supports it.

5. Transport, storage and data protection

Public AGRO-AI product endpoints use HTTPS/TLS. Production customer data stores and object-storage paths are expected to use platform-provided encryption and access controls appropriate to the service.

Because encryption behavior can differ by storage layer, vendor and customer configuration, AGRO-AI does not use blanket statements such as “everything is encrypted everywhere” unless the exact scope has been verified and documented in the Trust Claims Register.

Restricted Operational Data receives heightened handling requirements under the Data Governance Standard.

6. Logging, auditability and monitoring

AGRO-AI uses operational and security telemetry to support reliability, abuse prevention, troubleshooting, incident investigation and appropriate auditability. Logs should avoid unnecessary secret or sensitive-content capture and should be subject to bounded access and retention.

Where a product workflow exposes audit history, provenance or decision records, those records are designed to help authorized teams reconstruct material actions and evidence rather than rely on memory.

7. Secure development and change control

  • Security-sensitive changes should receive code review and automated checks appropriate to the component.
  • Production and staging boundaries should be explicit so tests do not silently target live customer systems.
  • Configuration and feature flags should fail closed for high-risk capabilities where practical.
  • Secrets should not be committed to source control.
  • Dependencies and infrastructure should be updated and reviewed based on risk.
  • Material security/privacy changes should update the corresponding data-flow and trust documentation.

8. Connector and integration security

Connected agricultural systems can carry high-value credentials and operational data. Connector governance therefore includes customer authorization, requested scopes, token/secret storage, webhook validation where applicable, revocation, downstream data use and write/actuation permissions.

Read access does not automatically authorize write-back or physical action. Capabilities that can change external systems require separate product and authorization controls.

9. AI-specific security boundaries

  • Tenant isolation and authorization occur before retrieval and model context assembly.
  • Uploaded files, notes, transcripts, imagery metadata and integration strings are treated as untrusted data rather than system instructions.
  • Prompt-injection content inside evidence should not be allowed to grant new permissions or override authorization policy.
  • Action tools should accept typed/validated parameters and enforce authorization outside the model.
  • Consequential actions remain approval- and capability-bound.

See the AI Data Use Policy for model-provider and training boundaries.

10. Backup, recovery and continuity

AGRO-AI's operational standard includes backups/recovery appropriate to the relevant system, incident recovery procedures and evidence of critical infrastructure behavior. Recovery objectives can vary by service and customer agreement.

Backup systems also affect deletion timelines. We describe deletion and backup aging honestly rather than promising instant disappearance from every historical copy.

11. Incident response

The incident process is expected to cover detection, triage, containment, evidence preservation, severity assessment, internal escalation, customer/legal analysis, notification, recovery and post-incident remediation.

Notification timing and content are governed by applicable law and the relevant agreement. AGRO-AI will not publish a breach-notification promise that is broader than the team's implemented detection and response capability.

12. Vendor and subprocessor risk

Providers that can access Customer Data, personal information, Restricted Operational Data or credentials require review appropriate to their risk. Review includes service scope, security, confidentiality, incident obligations, retention, deletion, data-use/training terms, locations/transfers and downstream subprocessors where relevant.

See Subprocessors & Integrations.

13. Assurance and certification status

No invented compliance badges.

AGRO-AI does not represent that it has a SOC 2 report, ISO 27001/27701 certification or other independent certification unless that report or certificate has actually been issued and applies to the relevant scope.

Security frameworks such as NIST, SOC 2 criteria and ISO standards can guide control design and readiness without implying certification. Our preferred sequence is evidence baseline, risk-driven independent testing, readiness work and then formal assurance when customer demand and company maturity justify it.

14. Report a security concern

If you believe you have found a security issue involving AGRO-AI, do not include sensitive customer data, credentials or exploit material in a public forum. Contact contact@agroai-pilot.com with a concise description and a safe way to reproduce the issue. We will route it for security review.
